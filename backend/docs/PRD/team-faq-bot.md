# Team FAQ Chatbot — PRD

## 1. Overview

New hires and team members repeatedly ask the same operational questions (PTO policy, laptop provisioning, deploy process) via Slack, creating unnecessary interruption load on teammates and leads. Authoritative answers are scattered across a wiki that is rarely maintained, resulting in stale or inconsistent guidance.

The Team FAQ Chatbot ("FAQ Bot") provides a lightweight, scoped question-answering interface backed by a single admin-managed FAQ file per team. A user types a natural-language question in a chat UI or calls a REST endpoint; the bot retrieves the most relevant FAQ content and uses Amazon Bedrock to compose a cited answer. If no relevant content is found the bot explicitly replies "not in FAQ" rather than hallucinating an answer. Admins refresh content by replacing the FAQ file — no database migrations or fine-tuning required.

The MVP is intentionally single-team in scope. Cross-team federation, document RAG pipelines, and full chat-history storage are explicitly deferred to preserve simplicity and avoid PII risk.

## 2. Goals & Success Metrics

| Goal | Metric | Target | Notes |
|------|--------|--------|-------|
| Deflect repetitive onboarding questions | % of tracked onboarding question categories answered by bot without human escalation | ≥ 70 % within 30 days of rollout | Measured via gap-list review |
| Answer accuracy | Admin review of random sample of bot answers rated "correct and cited" | ≥ 90 % of sampled answers | Bi-weekly spot-check |
| Reduce Slack interrupts | Qualitative feedback from team leads | Noticeable reduction reported | Survey after first month |
| Admin content freshness | Mean time to update FAQ after policy change | < 1 business day | Admin replaces file; no engineering required |
| Identify knowledge gaps | Number of "not in FAQ" questions logged and triaged weekly | Gap list reviewed at least weekly | Drives FAQ improvement loop |

---

## 3. Non-Goals / Out of Scope

- Cross-team FAQ access or mixing multiple teams' content in one query
- Full document RAG over PDFs, Confluence, Notion, or other rich formats beyond a plain-text FAQ file
- Persistent full chat transcripts or per-user conversation history
- Storage or processing of personally identifiable information (PII) in any log
- Fine-tuning or retraining of any language model
- Slack or MS Teams native bot integration (UI surface is web chat + REST in MVP)
- User authentication / SSO (deferred; see Open Questions)
- Multi-language support
- FAQ file sizes exceeding 50,000 characters in v1
- Versioned FAQ history or rollback beyond replacing the current file

## 4. Users & Use Cases

| Persona | Need | Primary use case |
|---------|------|------------------|
| New Hire | Get quick, accurate answers to onboarding questions (PTO, laptops, deploy) without waiting for a human | Types a question into the chat UI and receives a cited answer immediately |
| Existing Team Member | Self-serve on process questions without interrupting colleagues | Uses the REST endpoint or chat UI mid-workflow to check a policy detail |
| Team Admin | Keep FAQ content current with minimal effort | Uploads a new plain-text FAQ file via the admin UI to replace the current collection |
| Engineering Lead / Team Lead | Understand what questions the bot cannot answer so the FAQ can be improved | Reviews the weekly gap list (unanswered or "not in FAQ" questions) |

## 5. Functional Requirements

| ID | Description | Priority | Acceptance criteria (Given / When / Then) |
|----|-------------|----------|---------------------------------------------|
| FR-1 | **FAQ File Upload (Admin)** — An admin can upload a single plain-text FAQ file (Q&A pairs or bullet topics) to replace the team's current FAQ collection. | P0 | **Given** an authenticated admin user on the admin upload page, **When** they submit a valid plain-text file ≤ 50,000 characters, **Then** the system stores the file, replaces the previous collection, and returns an HTTP 200 with a confirmation message within 5 seconds. |
| FR-2 | **File Size Validation** — The system rejects FAQ files exceeding 50,000 characters. | P0 | **Given** an admin attempts to upload a file > 50,000 characters, **When** the upload request is submitted, **Then** the system returns HTTP 400 with a human-readable error message stating the size limit, and the existing FAQ collection remains unchanged. |
| FR-3 | **REST Ask Endpoint (`POST /ask`)** — The system exposes a REST endpoint that accepts a natural-language question and returns a bot answer. | P0 | **Given** a valid JSON body `{"question": "<text>"}` is sent to `POST /ask`, **When** matching FAQ content exists, **Then** the system returns HTTP 200 with a JSON body containing `answer` (generated by Bedrock) and `citation` (the FAQ section or question heading used), within the latency SLA defined in NFR-1. |
| FR-4 | **"Not in FAQ" Fallback** — When no relevant FAQ content matches the question, the bot must reply with a clear "not in FAQ" message and must not generate a speculative answer. | P0 | **Given** a question is submitted that has no matching content in the current FAQ file, **When** Bedrock evaluation and retrieval both return no relevant context, **Then** the API response contains `{"answer": "This question is not covered in the FAQ.", "citation": null}` and no generated content is included. |
| FR-5 | **Citation in Answer** — Every successful answer must reference the FAQ section or question heading from which it was derived. | P0 | **Given** a question that matches FAQ content, **When** the answer is returned, **Then** the `citation` field in the response is non-null and corresponds to an identifiable heading or Q label present in the uploaded FAQ file. |
| FR-6 | **Chat UI** — A Streamlit-based chat interface allows users to type questions and view answers with citations in a conversational layout. | P0 | **Given** a user opens the Streamlit chat UI, **When** they type a question and submit, **Then** the UI displays the bot's answer and citation (or "not in FAQ" message) without page reload, and the question input field is cleared for the next question. |
| FR-7 | **Streamlit Role-Based Views** — The Streamlit app presents a standard chat view to regular users and an admin upload panel to admin users, with login flow and error display. | P1 | **Given** a user authenticates as an admin, **When** they access the app, **Then** the admin panel (file upload) is visible; **Given** a non-admin user authenticates, **Then** only the chat view is accessible and the admin panel is hidden. |
| FR-8 | **Question Logging for Gap Analysis** — Every question submitted to `POST /ask` is logged with its timestamp and whether the bot answered or returned "not in FAQ", without storing PII or the user's identity. | P0 | **Given** any question is submitted, **When** the response is returned, **Then** a log entry is written containing: anonymized question text, timestamp, and answer status (`answered` / `not_in_faq`). The log must not contain user identifiers, IP addresses, or full conversation context. |
| FR-9 | **Gap List Export** — Team leads can retrieve a list of questions that received a "not in FAQ" response, queryable by date range. | P1 | **Given** a team lead calls `GET /gaps?from=<date>&to=<date>`, **When** the date range is valid, **Then** the response returns a JSON array of logged unanswered questions within that range, sorted descending by timestamp. |
| FR-10 | **Single-Team Scope Enforcement** — The system operates with one active FAQ collection at a time; no mechanism exists to query across multiple team collections in a single request. | P0 | **Given** the system holds one FAQ collection, **When** any `POST /ask` request is processed, **Then** only the single active collection is consulted and no cross-team data is accessible via the endpoint. |

## 7. Data & Integrations

**Core Data Entities**

| Entity | Description | Storage notes |
|--------|-------------|---------------|
| `faq_collection` | The single active plain-text FAQ file for the team; replaces previous on upload | Stored as a flat file or single text blob; one record active at a time |
| `question_log` | Anonymised record of each question asked: `{id, question_text, timestamp, status: answered|not_in_faq}` | Append-only log table; no user FK; purged after retention window |
| `gap_list` | Derived view / query over `question_log` where `status = not_in_faq` | No separate storage; query-time filtered |

**External Integrations**

| System | Role | Notes |
|--------|------|-------|
| Amazon Bedrock | LLM answer generation with FAQ context injected into prompt | Model selection TBD (see Open Questions); Bedrock API called server-side only; credentials via IAM role |
| Streamlit | Chat UI and admin upload panel | HTTP client to FastAPI only — never imports `app/` modules directly |
| FastAPI | REST API layer under `target-apps/team-faq-bot/` | Exposes `POST /ask`, `POST /upload`, `GET /gaps`; OpenAPI spec auto-generated |

**Data Flow Summary**

1. Admin uploads `.txt` FAQ file → FastAPI validates size → stores as active collection.
2. User question → `POST /ask` → FAQ content retrieved → prompt constructed (FAQ context + question) → Bedrock generates cited answer → response returned + question logged.
3. Team lead calls `GET /gaps` → query over question log → returns unanswered questions.

## 8. Analytics & Observability

**Logging**
- All API requests logged in structured JSON with: `request_id`, `endpoint`, `http_status`, `duration_ms`, `timestamp`.
- Bedrock call events logged with: `request_id`, `model_id`, `prompt_token_count` (if available), `duration_ms`, `outcome (answered|not_in_faq|error)`.
- Upload events logged with: `admin_role` (not identity), `file_size_chars`, `timestamp`, `outcome`.
- No question text from `question_log` must appear in application-level debug logs beyond the dedicated log store.

**Metrics & Alerts**
| Metric | Alert threshold |
|--------|----------------|
| `post_ask_p95_latency_ms` | Alert if > 5,000 ms over 5-minute window |
| `not_in_faq_rate` | Alert if > 60 % of hourly requests are unanswered (possible broken FAQ) |
| `bedrock_error_rate` | Alert if > 5 % of Bedrock calls error in 10-minute window |
| `faq_collection_age_days` | Warning if active FAQ file not updated in > 30 days |

**Gap Analysis Dashboard (lightweight)**
- `GET /gaps` response feeds a Streamlit admin view showing unanswered questions grouped by recurrence, enabling admins to prioritise FAQ additions.

## 9. Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Bedrock returns a plausible-sounding answer when context is thin, leaking beyond FAQ scope | High — erodes trust; violates "no guessing" requirement | Enforce strict prompt instruction: "Answer ONLY from the provided FAQ text. If the answer is not present, respond with the exact phrase: not in FAQ." Add automated test asserting the fallback for out-of-scope questions. |
| FAQ file becomes stale; answers are outdated | Medium — new hires receive wrong guidance | `faq_collection_age_days` metric alert at 30 days; gap list review cadence drives updates |
| Admin accidentally deletes active FAQ (empty upload) | High — all queries return "not in FAQ" | Validate that uploaded file is non-empty and contains at least one recognisable Q&A or bullet item before replacing active collection |
| Bedrock API latency spikes breach UX threshold | Medium — users abandon bot, return to Slack pings | Implement client-side timeout with user-facing "try again" message; monitor p95 latency alert |
| PII inadvertently included in question text logs | High — privacy / compliance breach | Log only question text stripped of patterns matching email/phone via regex sanitiser before write; document in privacy policy |
| 50k char limit too restrictive for growing teams | Low (MVP) | Hard limit enforced in v1; file chunking or multi-file support scoped to v2 |

## Appendix: Assumptions

- **Authentication**: No auth mechanism is specified in the brief. It is assumed that at minimum the admin upload endpoint requires authentication (API key or JWT). The public `POST /ask` endpoint may be open within a trusted internal network, pending security review.
- **Deployment target**: AWS-hosted (consistent with Bedrock usage) but specific compute service (ECS, Lambda, EC2) is not specified; architecture should be container-friendly.
- **Bedrock model**: A capable instruction-following model (e.g., a Claude variant) is assumed; final selection is pending cost/latency evaluation.
- **FAQ file format**: Plain text is specified; it is assumed that a structured format (e.g., `Q:` / `A:` prefix pairs) will be recommended to improve citation extraction, but free-form text will also be supported with degraded citation granularity.
- **Single deployment = single team**: One running instance of the service maps to one team; multi-team support would require separate deployments or a tenant layer not in scope for MVP.
- **No vector database**: Given "not full document RAG" and the 50k char constraint, it is assumed that FAQ content is injected directly into the Bedrock prompt context (full or top-N matched sections via simple keyword/embedding match), rather than a vector store pipeline.
- **Gap list is not PII-sensitive**: Questions logged for gap analysis are assumed to be operational/process questions. A sanitiser is applied as a precaution but no full PII review workflow is assumed.
- **Performance targets**: p95 ≤ 4 s for `/ask` and 99.5 % uptime are reasonable defaults for an internal tool; these are assumptions pending stakeholder agreement.
- **Data retention**: 90-day log retention assumed as a reasonable default; subject to organisational policy.
- **Streamlit is the MVP UI**: No mention of a separate React frontend; Streamlit is confirmed as the v1 client surface.
- **No Slack integration in MVP**: The problem mentions Slack as the current interrupt channel, but the bot surface is a standalone web UI + REST endpoint; Slack integration is a potential v2 feature.
