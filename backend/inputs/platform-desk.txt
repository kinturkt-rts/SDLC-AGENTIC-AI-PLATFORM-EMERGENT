Platform Runbook Vector Desk — on-call symptom search over structured runbook steps

Client story:
The platform SRE team supports dozens of internal microservices. When PagerDuty fires, engineers
grep Confluence and old Slack threads for "Redis connection pool exhausted" or "Kafka consumer lag
fix." Runbooks exist but are inconsistent: some are one paragraph, others are thirty steps across
three services. On-call wants to paste an alert summary or error snippet and get ranked runbook
*steps* (not whole pages), see which service owns the fix, and record which runbook was used when
closing an incident.

This is not a generic wiki or HR policy site. It is an operations runbook desk with structured
procedures, service linkage, meaning-based search over steps, and a simple browser console for
on-call workflows.

MVP:
- Service catalog: each microservice has a name, owning team, criticality tier (1–3), and whether
  it is still in active support.
- Runbooks: title, linked service, default severity (low / medium / high / critical), short summary,
  author, and lifecycle status — draft, active, or retired. Only active runbooks appear in on-call
  search and default browse. Retired runbooks stay for history but are hidden from search.
- Runbook steps: ordered steps with title and body text; optional estimated minutes and an optional
  warning callout. Long steps should still surface the right passage in search, not only the title.
- Symptom search: on-call types natural-language alert text; system returns the best-matching steps
  ranked by meaning, with service name, runbook title, step number, and a short excerpt. At most one
  hit per runbook in a single result set (keep the best-matching step).
- Filter search by service when the alert clearly belongs to one system.
- Similar-runbook check: when an editor prepares to activate a draft, show a few existing active
  runbooks that read similarly (advisory only — they may still activate).
- Incident touch log: after using a search result, on-call can record a ticket reference, which
  runbook (and optionally which step) was used, and short notes. Admins see which services rely on
  which runbooks over the last month.
- Search analytics (admin): frequent queries, queries with weak or no useful matches, typical
  response time. Aggregated views only — no naming individuals in coverage reports.
- Optional plain-English one-liner on search results summarizing the top hit; when confidence is
  low, say so instead of guessing.

Personas (who needs what):
- Viewer (on-call) — symptom search, browse active runbooks and steps, log incident touches.
- Editor — create and edit draft runbooks and steps, check similar runbooks, activate or retire.
- Admin — manage the service catalog, view search analytics, refresh search index when content
  changes materially.
- Public / unauthenticated — health check only.

Business rules worth getting right:
- Cannot activate a runbook with no steps.
- Cannot have two active runbooks with the same title for the same service.
- Search and default browse never show draft or retired runbooks.
- Retiring a runbook removes it from search immediately; history and incident touches remain.
- Similar-runbook suggestions compare against active runbooks only.
- Estimated minutes and warning callouts are optional on steps.
- Viewers cannot create or edit runbooks or services; editors cannot manage the service catalog
  or org-wide analytics.
- Incident touch requires a ticket reference; notes are optional.

Demo data expectations:
- 8–10 services across tiers 1–3 (e.g. payments-api, auth-gateway, batch-reporter).
- 12–15 runbooks: about eight active, three draft, two retired.
- 60+ steps total; at least three runbooks with eight or more steps and long bodies for search demos.
- Pairs of runbooks with overlapping topics (e.g. two Redis or database connection guides with
  different wording) to demo similar-runbook warnings and ranking.
- Sample search history and incident touches so analytics screens are not empty.
- Realistic author and team names.

UI expectation:
- Streamlit (or equivalent) role-gated experience:
  - On-call search: paste alert text, optional service filter, results with excerpts and “used for
    incident” logging.
  - Browse: filter by service; expand runbooks to read ordered steps.
  - Editor: draft runbooks, step editor, similar-runbook panel, activate / retire actions.
  - Admin: service list, search analytics, way to refresh search after bulk edits.
- API is source of truth; UI calls backend over HTTP.

Out of scope:
- PagerDuty or webhook ingestion, auto-remediation, SSH to production hosts
- Full ITSM (assignments, SLA timers, workflow engines)
- PDF upload, Confluence sync, SSO beyond simple dev roles
- Public internet exposure
