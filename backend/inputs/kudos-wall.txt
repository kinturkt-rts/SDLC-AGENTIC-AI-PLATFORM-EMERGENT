Team Kudos Wall — simple peer recognition for internal teams

Client story:
Riley leads a 40-person product team. Good work gets mentioned in chat and is forgotten by Friday.
People want a lightweight place to say thank you publicly — who helped, on what, and when — without
another heavy HR system. Managers should be able to highlight standout kudos for all-hands shout-outs.

MVP:
- Anyone can read the kudos wall: who was thanked, who wrote it, a short message, and the date.
- Team members can post a kudos for a colleague (one message per post; plain text, no attachments).
- Optional short "context" line (e.g. "shipped the release", "covered my on-call") — not required.
- Managers can mark a kudos as "featured" so it appears at the top of the wall until unfeatured.
- Only the person who posted a kudos can edit or delete their own post (within a reasonable window).
- Featured flag can only be toggled by someone with manager access.
- Search or filter the wall by recipient name or by words in the message.

Personas (who needs what):
- Team member — browse the wall; post kudos for others; edit or delete own posts.
- Manager — everything a team member can do, plus feature or unfeature any kudos.
- Visitor / reader — browse and search only (no posting).
- Anonymous — health check only for operations monitoring.

Business rules worth getting right:
- Cannot post a kudos with an empty message or empty recipient name.
- Recipient name is free text for MVP (no corporate directory integration).
- A user cannot feature their own kudos unless they are a manager (managers may feature any post).
- Default wall view shows featured kudos first, then newest non-featured.
- Deleting a kudos removes it from the wall but managers asked for posts to be soft-deleted in the
  database when possible so history can be audited later.
- List views should support paging when the wall grows.
- The browser UI must load and save data through the backend over HTTP — the API is the source
  of truth, not direct database access from the UI.

Demo data expectations:
- At least eight kudos across three weeks with realistic names (e.g. "Jordan Lee", "Sam Patel").
- Two featured kudos and several regular ones.
- Mix of short and slightly longer messages so search is easy to demo.
- At least one kudos posted by a manager and several by regular team members.

UI expectation:
- Streamlit web app with at least:
  - **Wall** — scrollable list, featured section at top, search box.
  - **Post kudos** — form: recipient name, message, optional context; submit as team member.
  - **Manager tools** — feature / unfeature buttons when logged in as manager.
- Clear errors when the API is unreachable or the user lacks permission.
- API on port 8000; Streamlit on port 8501 for local demos.

Out of scope:
- Slack or Teams integration, email digests, badges or points/gamification
- User profile photos, file attachments, reactions or comment threads
- Full HR performance reviews, compensation, or org-chart sync
- AI-generated messages, multi-tenant public sites

Success criteria:
- Full pipeline produces a working app under target-apps/ with passing automated tests.
- README explains how to configure the environment, apply database seed data, and run API + UI.
- Demo: browse wall → post kudos → manager features one → search finds it.

Target app slug: team-kudos
Output directory: target-apps/team-kudos/
